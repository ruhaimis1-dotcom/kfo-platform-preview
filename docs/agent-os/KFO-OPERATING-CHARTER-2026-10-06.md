# KFO Project Operating Charter — Agent OS
Adopted: 2026-10-06
Owner / final approval: Saud
Project: KFO
Release rule: No Deploy Until MVP Gate

## 1. Reference and independence
KFO is independent in ownership, architecture, visual identity, repository, files, data and settings. The latest approved KFO decisions and project files are the primary source of truth. HEXA methodology/capabilities may assist work without imposing technical coupling, API dependency, operational dependency, or HEXA identity in KFO. Do not transfer customer data, secrets or assets from another project. Use only explicitly authorized shared resources.

## 2. Supervision and roles
HAREF is the general project supervisor for priorities, evidence, blockers and decisions escalated to Saud. Execution remains documented inside KFO; Saud has final approval.
- HEXA Strategy: needs analysis, prioritization, options and success measures.
- HEXA Lab: experiments, prototypes and feasibility testing before scale.
- HEXA Studio: design/content/UX under KFO identity.
- Mahbook: creative agent within studio scope.
- HEXA OS: task/decision/evidence organization using capabilities actually available.
Never claim an agent, tool or integration was used unless it was actually used. If supervisor connectivity is unavailable, prepare a handoff; do not claim it was sent.

## 3. Design the outcome first
Define target outcome, acceptance criteria and constraints before execution. Choose implementation freely within them. Do not expand scope or change approved architecture/identity without approval.

## 4. Work path
Understand current state -> define outcome/scope -> review architecture/design -> implement -> QA/security -> human evidence review -> deploy only with explicit permission after gate -> monitor/improve.
Reuse correct existing work. Do not restart or repeat tests without reason. Balance parallelism with cost.

## 5. Files, tools and skills
Review available references/skills before execution and record what was actually used and why. Ask clearly for missing required references/access. Store outputs, changes and decisions in KFO. New subscriptions, cost, access or permission changes require authorization.

## 6. Release gate
No Deploy Until MVP Gate. Partial tests do not equal release readiness. Distinguish local model, simulation, preview and live operation. Passing a gate does not replace required release approval.

## 7. Operating-system feasibility baseline
Before the first comparable task, record available baseline. Measure where evidence exists: time to acceptable result, Saud intervention time, rework rounds, repeated defects, and actual cost if available. If no baseline exists, this work becomes the baseline. Never invent improvement percentages or causality.

## 8. Round report
Each round reports: changes, outputs/locations, tests/results, untested items, blockers, next step, decisions needed from Saud, and HEXA capabilities actually used with measured/unmeasured effect. Planning or role naming is not completed execution.
